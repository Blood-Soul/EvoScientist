# 跨论文 L1 → L2 归纳（cross-paper induction）

状态：设计 + 第一版实现（branch `feat/cross-paper-l2`，2026-11-19）。所有阈值都是暂定值，按实验结果再调。

## 1. 目的

单篇论文内的归纳（`l2_from_l1_v2.md`）只能看到一篇论文自己的几个实验，r35 的 44 条归纳 L2 里来源跨论文的是 0 条。
这里要做的是：把**不同论文里解决同一类问题、用同一类方法**的 L1 放在一起，归纳出更抽象、可迁移的 L2——
"在什么条件下这一类做法有效、为什么、代价是什么、不同论文在哪里结论不一致"。

L2 的文字不要求在 L1 里逐字出现（这是从具体到抽象的一步），但**每一条结论都要说清依据的是哪几条 L1**，
来源列表由代码维护，模型不能悄悄丢掉或编造来源。

## 2. 参考过的做法（摘要）

| 做法 | 借鉴什么 | 不照搬什么 |
|---|---|---|
| RAPTOR (2401.18059) | 先聚类再对簇做总结 | 一次性离线重建、无出处 |
| GraphRAG (2404.16130) | 社区报告引用元素 id | 需要实体图、无增量 |
| Zep/Graphiti (2501.13956) | **新记录按邻居归入已有簇，簇摘要增量更新；定期全量刷新**，因为增量簇会逐渐偏离全量结果；冲突的旧结论标为失效而不是删除 | 时序图 |
| ACE (2510.04618) | **用增量操作而不是整段重写**：整段重写出现过"上下文坍缩"（18k token 缩到 122，准确率 66.7→57.1） | — |
| ExpeL (2308.10144) / Mem0 (2504.19413) | ADD / EDIT / DOWNVOTE / DELETE 这类操作；结论要能被新证据削弱 | 无出处的投票 |
| Generative Agents (2304.03442) | `insight (because of 1, 5, 3)` 这种最简单的出处格式 | — |
| AutoGuide (2403.08978) | 结论必须绑定"适用情境"，否则跨来源的结论会被用错地方 | — |
| BERTopic / HDBSCAN | **允许离群点**：不强行把每条记录塞进一个簇 | — |

文献里**没有**直接比较"增量操作 vs 整簇重写"对总结质量影响的实验，也没有关于最小簇大小的实证；下面的设定是基于这些间接证据的设计选择。

## 3. 流程

```
新 L1 入库（每篇论文抽取 + gate 之后）
   │  计数器 +n
   ▼
累计新增 L1 ≥ N（暂定 15）？──否──> 等待
   │是
   ▼
是第 K 次触发（暂定每 3 次）或还没有任何簇？──是──> 全量重建
   │否
   ▼
增量更新
```

### 3.1 相似度（不依赖外部 embedding API）

容器里没有 embedding 服务，`api.jina.ai` 不在白名单里，evosci 的 venv 里也没有 torch。第一版用**按字段加权的 TF-IDF 余弦**：

- 视图文本 = `problem` ×2 + `method`（名称 + 别名）×2 + `task` + `requires` + `action`。
- 去掉停用词和领域里到处都有的泛词（model / training / performance ……），IDF 在当前库上算。
- 只看**不同论文**之间的相似度。

离线在 r35 的库上（81 条 L1，22 篇论文）实测过：跨论文余弦 ≥ 0.15 的只有 12 对，最高 0.29。
所以**词面相似度只用来提名候选**，是否同类由 LLM 判断（ClusterLLM 2305.14871 的做法：小模型/词面提名，LLM 裁决）。

### 3.2 全量重建

1. 对每条 L1 取跨论文最近的 k=6 个邻居，余弦 ≥ τ_nominate（暂定 0.08）的作为候选边。
2. 候选边按连通分量 + 大小上限（暂定 8）切成候选组；超过上限的组按平均链接再切。
3. **LLM 分组**：把一个候选组里的 L1（只给 problem / method / task / action 摘要和 id）交给模型，让它把"在解决同一类问题、或在比较同一类做法"的记录分成若干簇，并给每个簇写一句**适用情境**（AutoGuide 的 context）。模型可以把记录留作离群点。
4. 只保留**至少 2 篇不同论文、至少 3 条 L1**（暂定；2 篇论文 2 条也允许）的簇。
5. 对每个簇调用归纳 prompt 生成 L2（见 §4）。
6. 新簇的 L2 和上一版的 L2 按来源重合度对齐（Jaccard ≥ 0.5 视为同一簇）：对得上的沿用 id、记录版本；对不上的旧 L2 标为 `retired`（保留在文件里，不再被检索），不直接删除。

### 3.3 增量更新

1. 对每条新 L1，算它和每个现有簇的相似度（簇内 L1 的最大余弦 + 平均余弦）。取最相近的 3 个簇给 LLM 判断归属，或判为"不属于任何簇"。
2. 归入某簇的新 L1 加进簇的成员表（代码维护）。
3. 有新成员的簇调用 **修订 prompt**：给出当前 L2 和新成员 L1，让模型只输出**操作**：
   - `KEEP`：新证据不改变结论；
   - `REVISE`：结论需要调整，给出修改后的字段（只改受影响的字段）；
   - `ADD_CONFLICT`：新证据和已有结论冲突，追加到 `conflicts`，**不覆盖**原结论；
   - `RETIRE`：新证据推翻了这条 L2（极少）。
   修订后正文长度不得少于原来的 60%（防止 ACE 那种坍缩），否则拒绝这次修订。
4. 没归入任何簇的新 L1 进入"暂存池"；暂存池里如果能凑出满足 §3.2 第 4 条的新组，就对这一组单独做一次 §3.2 的第 3–5 步。
5. 全部 L2 带版本号和上一版文本，便于事后对比增量结果和全量重建结果的差异。

## 4. 跨论文 L2 的格式

沿用当前 L2 的字段，`origin` 新增取值 `cross_paper`：

```json
{
  "domain": "...", "task": "...",
  "problem": "这一类问题，用实践者在知道答案之前的话说",
  "method": ["这一类做法的名称", "别名"],
  "context": "这条结论适用的情境（簇的定义）",
  "action": "归纳出的结论，写成指令：什么时候做什么、换来什么",
  "compared_options": [{"option": "...", "result": "...", "from": ["E-..."]}],
  "mechanism": "多篇论文共同支持的原因；没有就留空",
  "requires": [{"text": "...", "basis": "inferred", "from": ["E-..."]}],
  "limits_stated": [{"text": "...", "from": ["E-...", "E-..."]}],
  "conflicts": [{"text": "A 论文发现……而 B 论文发现……", "from": ["E-...", "E-..."]}],
  "origin": "cross_paper",
  "source_l1_ids": ["E-...", "E-..."],
  "source_papers": ["2101.00438", "2108.05857"],
  "version": 1
}
```

规则（在代码里检查，不只写在 prompt 里）：

- `source_l1_ids` 由代码填写为簇成员；模型给出的每个 `from` 必须是簇成员，否则这一条被删掉。
- 整条 L2 至少依据 2 篇不同论文；单篇论文就能支持的结论留给单篇内归纳去做。
- `limits_stated` 只能总结成员 L1 里作者原话的局限（至少引用 2 条有局限的 L1，与单篇内归纳的规则一致）；不从代价里取，不从机制里推。
- `compared_options` 里的数字必须出现在所引 L1 里，不做加减、平均或外推。
- 结论之间有冲突时写进 `conflicts`，不抹平。

## 5. 存储

跨论文 L2 不属于任何一篇论文，存在项目目录下的独立文件：

```
experiences/projects/<P>/_cross_paper/
  metadata.json   # 让现有的 list_experience_documents 把它当作一个"虚拟论文目录"读取
  l2.json         # 当前有效的跨论文 L2
  state.json      # 簇成员、已处理的 L1 id、计数器、版本历史、retired 的 L2
```

这样检索、渲染、plan review 都不用改读取路径。渲染时标为 "L2 finding · induced across N papers"。

## 6. 运行方式与开关

- 开关 `memory_cross_paper_enabled`（环境变量 `EVOSCIENTIST_MEMORY_CROSS_PAPER_ENABLED`），默认关闭；只有新的实验臂打开。
- 触发点：论文经验 worker 每完成一批（一次 drain）后检查计数器；在 drain 持有的队列锁之外运行，另用一把锁保证同一时刻只有一个归纳任务。
- 并发：LLM 调用并发 6（用户给的范围 4–8）。
- 每次触发写一条 trace（`cross_paper_induce`：模式、簇数、新增/修订/退役的 L2 数、耗时、token），usage ledger 里可按调用来源区分。
- 失败只记录、不影响抽取和 agent 主流程。

## 7. 暂定参数

| 参数 | 值 | 依据 |
|---|---|---|
| N（触发间隔） | 15 条新 L1 | 6 小时约 80 条 L1，可触发 5–6 次 |
| 全量重建间隔 | 每 3 次触发 | Zep 建议定期刷新 |
| 最小簇 | 2 篇论文且 ≥3 条 L1（2 篇 2 条也允许） | 无实证，设计选择 |
| 候选组上限 | 8 条 L1 | 控制单次 prompt 长度 |
| 修订后最短长度 | 原文 60% | 防坍缩（ACE） |
| LLM 并发 | 6 | 用户给定 4–8 |

## 8. 验证计划

1. 离线：在 r35 的库上跑一次全量重建，人工 + LLM 抽查簇是否同类、L2 是否忠实于所引 L1、是否只是复述某一条 L1。
2. 离线：把 r35 的论文按入库顺序回放，模拟每 15 条触发一次，比较增量结果与最终全量重建结果的差异。
3. 在线：新实验臂 6 小时，统计触发次数、跨论文 L2 数量、被 plan review 引用的次数，以及 writer 对引用它们的建议的采纳情况。
