# 经验检索独立化改造

> 分支 `feature/search_experience_api`，四个提交：`f58036e` → `bcfa55c` → `aa8f8c1` → `e36e7b1`。
> 本文既是这次改动的汇报，也是下次回到这块代码时的交接说明：写清**为什么这么改**，
> 以及**哪些结论已经被验证过、哪些还没有**。

## 1. 问题

经验检索原本复用 `search_observations` 入口，两个库的文档被拼在一起交给同一个排序器。
症状是这样暴露的：给 agent 的任务是"根据这几篇论文的摘要，你想些 idea，然后去找出相似
idea 的论文"，它构造出来的 query 是

- `如何利用摘要完成idea的构建`
- `有哪些可以找论文的api`

这些是**过程性**的问法。而 `E-*` 记录全部来自论文抽取，里面只有**内容性**的发现——
论文做了什么、在什么设定下、测到什么结果。过程性问题在这个库里不可能有答案，所以检索
要么返回空，要么返回一页看起来很自信的噪声。

根因不是排序器不够好，而是**一个入口只能有一套词汇**。合并检索造成两个具体故障：

**故障一：经验检索被迫接受 observation 形状的参数。**
每条 `E-*` 都硬编码存为 `SEMANTIC`/`PROJECT`。于是调用方传
`memory_type=procedural`（"我要找怎么做 X"最自然的配法，而且工具 schema 主动鼓励这么传）
或 `scope=global`（"我要找通用方法论"最自然的配法），会**静默地把整个经验库从结果集里
移除**——98 条记录一条都不剩，而且没有任何信号说明发生了这件事。

**故障二：observation 的词汇变成了经验检索的词汇。**
调用方照着 observation 的说明书去问一个只存主题发现的库，问法系统性地错位。

## 2. 方案

拆入口。每个库自己教自己的问法，参数列表不同是因为问题不同，不为对称而对称。

| 入口 | 检索对象 | 面向的问题 |
| --- | --- | --- |
| `search_experience` | `E-*` 论文经验 | 内容性：关于某个**主题**，别人发现了什么 |
| `list_experience` | `E-*` 论文经验 | 我根本不知道库里有什么、库里怎么措辞 |
| `search_observations` | `O-*` 操作记忆 | 过程性：这件事该怎么做、失败了怎么办 |
| `read_memory` | 两者 | 按稳定 ID 读完整记录（`O-`/`E-` 前缀本身就是无歧义的路由） |
| `apply_experience` | `E-*` | 要**做决策**而不是补充上下文：把来源写死的值改绑到当前任务 |

`search_experience` 的参数是 `topic` / `method` / `task` 三个主题面，加
`discipline` / `domain` / `level` 三个精确过滤。**它不接受 `memory_type` 和 `scope`**——
这两个描述的是 observation 的 frontmatter，对 `E-*` 传进来只可能是空操作或静默清空。

三个主题面**分别检索再用 RRF 融合**（`RRF_K = 60`），不是拼成一个长 query。拼接会让
一个低信息量的 token 决定整个排序：它匹配到所有文档，所有文档得分相同，"排序"退化成目录
顺序，却仍然返回一整页看起来很自信的结果。分别检索再融合意味着文档必须在**某个面**上排得
靠前才能出现，而多个面的一致才能把它推上去。

`list_experience` 存在的理由是**检索是词法的**。调用方如果不知道库里的说法，就写不出能命中
的 query；而开放式任务（"关于 X 有哪些发现"）根本没有唯一正确的问法。按结构浏览
（discipline → domain → records）绕开了措辞问题。每一层都分页并报告总数，所以库长到多大
都是可走完的，而不是被静默截断——这是明确按"生产环境会有庞大数量"来设计的，不依赖当前库
很小这个事实。

## 3. 学科词表：跨学科不只是 CS

经验后续会涉及生物、物理、数学等大量非 CS 学科，所以分类是两层：

- `discipline`：**有界**的粗粒度学科词表，用来防止跨学科库对着化学问题返回计算机记录；
- `domain`：抽取侧自由书写的细粒度标签（如 `agent_learning`），不设词表。

`discipline` 有两个来源。默认从元数据里的 `domain_arxiv` 在**读取时**推导
（`resolve_discipline()`），所以不需要为它做任何 backfill。但有 4 篇论文的
`domain_arxiv` 在元数据里就是 `null`，对应 11 条记录落到 `other`——无从恢复，它们仍然可以
被浏览到。这正是为什么又加了一个**模型直接给出**的可选 `discipline` 字段：抽取提示词现在
要求"从论文本身判断，而不是从它发表在哪里判断"，判断不了就省略。写入前会校验它落在词表内，
并规范化大小写；给出词表外的值会让该条记录**抽取失败**，而不是静默写入一个查不到的学科。

## 4. 性能：按"库会很大"来做

两处优化，都在真实库（98 条记录 / 33 篇论文 / 项目 `P-76d3d859652cb0ee`）上量过：

| 操作 | 改前 | 改后 |
| --- | --- | --- |
| `list_experience_documents` | 21.5ms | 2.1ms |
| `experience_library_stats`（**每个模型请求**都要跑） | 20.8ms | 2.2ms |
| 单面检索 | 42.6ms | 9.7ms |
| 三面融合检索 | — | 17.9ms |

- **解析缓存**：按 mtime + size 校验，文件没变就复用已解析的文档对象。
- **token 记忆化**：`document_token_index()` 把分词结果缓存在 frozen dataclass 上
  （`object.__setattr__` 写入 `token_index` 字段，`compare=False`，不影响相等性）。

值得记住的一点：**三面融合检索（17.9ms）现在比改造前的单面检索（42.6ms）还快**。所以
"分别检索再融合"这个正确性上的改进没有付性能代价。排序结果经过逐条比对，98 条文档上
与改造前**逐位相同**（0 处并集不一致）——记忆化只省时间，不改分数。

## 5. 词法检索的诚实边界

排序器的分词是 `[a-z0-9_]+`。中文 query 只剩下它恰好包含的拉丁片段：
`如何利用摘要完成idea的构建` → 只剩 `idea` 一个 token，而 `idea` 匹配库里大部分记录，
于是返回一整页高分结果，和问题毫无关系，而**响应里没有任何地方说明这件事**。

`degenerate_facets()` 现在报告这件事：按字符统计分词覆盖率，低于 `0.4` 就在响应里加一个
`query_warning`，写明"实际只搜了什么"（`searched_as: ['idea']`，`coverage: 0.27`），
并指向 `list_experience` 去看库自己的词汇。

它**不**做翻译或查询扩展——只报告真实搜了什么，让调用方看到排序建立在一个碎片上，然后
自己重述。用字符而不是 token 算覆盖率，因为"长 query 只活下来一个 token"正是最该报告的
情况。措辞良好的英文 query 不会触发。

## 6. 经验复用层没有被破坏

拆检索时最大的风险是把 `apply_experience`（"把过去旧的轨迹经验复用迁移到新的场景下"）
搞坏。它和 `search_experience` **共用同一个检索内核**：
`gather_candidates()` → `search_experience_records()`。已验证：

- `gather_candidates()` 对真实 query 返回 8 条完整记录，字段完好；
- ID 方案改成内容寻址后仍然可用（见下）。

### ID 从位置寻址改成内容寻址

`E-*` ID 现在是 `SHA256(project:paper:level:identity)[:16]`，`identity` 由
`statement`/`declaration`/`domain`/`task` 用 `\x1f` 连接。改之前 ID 含记录在数组里的
下标，重新抽取导致顺序变化时，**同一个 ID 会指向另一条发现**。

这个改动安全，因为 ID 是**读取时派生**的，不存在 `l1.json`/`l2.json` 里，不需要迁移。
唯一的存量影响是策略缓存里有一条以旧 ID 为键的记录——检索再也产生不出那个 ID，所以它
只会缓存未命中并重新合成，而不会拿一份基于**别的记录**建出来的策略去应答。

测试非空验证过：强制走回下标兜底路径，`test_experience_ids_follow_content_not_position`
会失败，且失败形态正是"同一个 ID 指向了另一条发现"。

## 7. Backfill：让复用层不再降级运行

`transferable_core` 和 `bindings` 是在库里已经有记录之后才加进抽取提示词的，所以所有
存量 `E-*` 都缺这两个字段。它们在读取时是可选的，但缺了会让复用层**降级运行**：

- `policy.select.transferable_core()` 退化成取 `statement` 前 200 字符当重排描述符——
  重排器看到的是一个被截断的段落开头，而不是那条论断；
- 策略写手的 `rebind` 步骤只能从散文里挖源侧写死的值，而不是读一个结构化列表；A/B 脚本
  也没法统计 stale-binding 命中。

`scripts/backfill_experience_fields.py` 从记录**自己已有的文本**派生这两个字段，不重新
下载论文、不重跑完整抽取。因为它就地编辑活的记忆库，而**存储本身就是这个库**（半个写坏的
`l1.json` 会丢掉里面所有记录，而且没有上游可以重新派生），所以安全属性是重点：

- **幂等**：字段已非空就跳过，所以中断的运行靠重跑就能续上。`--overwrite` 强制重新生成。
- **可续跑、可分批**：按论文提交，不按整次运行提交。`--limit` 限的是这次**真正处理**的
  论文数，不是走过的论文数——否则每一遍都会把预算花在已完成的前缀上，比一批更大的库
  永远跑不完，而这正是这个参数存在的意义。（这个 bug 是它自己的测试发现的。）
- **绝不破坏**：同目录临时文件 + `fsync` + `os.replace` 原子替换，且只在整份新文档都已
  落盘之后。写一半崩溃留下的是完好的原文件。`--backup` 额外留一份 `.bak`。
- **不假设 dry-run**：必须显式给 `--apply` 或 `--dry-run`。
- **输入太差就不写**：`statement` 短于 40 字符的记录报告为"太薄"而跳过。写一个从残桩派生
  的 core 比留着那个有文档记录的兜底更糟，因为**字段一旦存在，兜底就不再生效**。
  同理，模型判定论断不可迁移时返回空串，此时只写 `bindings`，让 `transferable_core`
  保持缺席。

### binding 必须是名字，不能是测量值

第一次真实运行产出了 `91%`、`80%` 这种被标成 `metric` 的 binding。A/B 脚本按子串匹配
binding，所以这类值**什么都标识不了**，而且会在任何恰好含这些字符的文本上误命中，把所有
条件的 stale 率一起抬高。两处同时修：提示词说清"binding 是**具名实体**，不是测量结果"，
并且在 `_parse_response` 里加确定性过滤 `_is_usable_binding()`——消费方的正确性不应该
依赖模型有没有照做。

### 真实库上的执行结果

```
papers: 33 seen, 30 wrote
records: 98 seen, 90 wrote, 8 already populated, 0 too thin to derive, 0 failed
```

全库审计：

- `transferable_core`：98/98 已填充，**没有任何记录仍在走截断兜底**；
- `bindings`：363 条，分布在 8 个 kind 上，**0 条不可用**（无裸数字、无短于 3 字符的名字）；
- 21 条 `bindings` 为空，**全部是 L2**。抽样核对过：这些归纳性论断确实没有点名任何源侧
  固定实体，空数组是准确的，不是漏派生。

不是只看文件，而是从**消费方**验证：`gather_candidates()` 对真实 query 返回 8 条候选，
描述符全部是真正的可迁移论断，兜底计数为 0。这就是 backfill 存在的目的。

## 8. A/B 脚本的一个真 bug

`scripts/policy_ab.py` 把 `--model` 的默认值文档化为"项目主模型"，却把未设置的参数直接
透传给 `get_chat_model`。而 `get_chat_model(model=None)` **不读项目配置**，它退回自己的
库内默认值，那是一个 Anthropic 模型。于是 12 个格子全部失败在
"缺 `ANTHROPIC_API_KEY`"——为了一个谁都没有选过的模型，而项目本身配的是完全另一个供应商。

修法：默认值从配置解析；解析时顺带把配置应用到环境变量。后半步是必要的——凭据写在配置
文件而不是 shell 里时，只有 `apply_config_to_env` 跑过之后 `get_chat_model` 才看得见它们。
Agent 走 `_ensure_auxiliary_chat_model` 自然获得这一步，独立脚本不会。两步都是
set-if-unset，所以显式参数和真实环境变量仍然优先。`--policy-model` 不动：
`derive_policy()` 传 `None` 时本来就会自己解析项目辅助模型。

新增 4 项测试。**其中 3 项在改前的行为下会失败**，所以它们确实钉住了这个 bug，而不是
陪着实现一起写的空测试。

## 9. A/B 结果：能跑通了，但还不是一个能引用的数字

复用层现在端到端跑通。最好的一次：

| 条件 | n | stale% | 每份计划 stale 数 | target% |
| --- | --- | --- | --- | --- |
| A 无记忆 | 2 | 50.0% | 1.00 | 87.5% |
| B 原始 `E-*` 散文 | 2 | 100.0% | 3.00 | 75.0% |
| C 派生策略 | 1 | 0.0% | 0.00 | 100.0% |

方向上与设计意图一致（散文 100% stale、每份计划抄 3 个源值；派生策略 0% stale 且
target 命中 100%）。但**这只是一个跑通信号，不是测量结果**，有两个必须一起说清的问题：

**样本量不够。** 12 格里有 7–8 格死于 `APIConnectionError`，每格只剩 n=1–2。

**条件 A 的绝对值不可信。** "无记忆"条件也拿到 50–100% stale，而如果这个指标真的在
度量"从注入的记忆里照抄"，这在结构上是不可能的。看命中的是什么就清楚了：`AdamW`、
`2e-5`、`0.1`——领域内任何一份像样的计划都会自己写出来的标准默认值，不是抄来的。
所以 **B−C 的对比仍然有意义，绝对 stale% 没有意义**；要让地板线真正读作 0，需要先把
这类通用值从 fixture 的 `bindings` 里去掉。

另外记一笔：条件 C 有一次真实失败于 `PolicyOutputError`，我复现并定位了——是辅助模型
输出抖动，不是代码缺陷（调用落地时 `derive_policy` 返回 `status: ok`，给出正常的
`adapt` 判决和面向目标任务的 procedure）。但 `PolicyOutputError` 这条路径会把它吞成
"失败的格子"，所以**写手偶发抖动和真正的功能损坏在报告里长得一模一样**。

## 11. 遗留

- **A/B 数字还不能引用**：需要更稳定的网络跑满 `--repeats`，并先把 `AdamW`/`2e-5`/`0.1`
  这类领域通用值从 fixture 的 `bindings` 里剔除，否则条件 A 的地板线读不出 0。
- **`PolicyOutputError` 掩盖了两种不同的事**：辅助模型偶发抖动和真正的功能损坏在报告里
  无法区分，值得分开计数或加一次重试。
- **11 条记录停留在 `discipline=other`**：来自 4 篇 `domain_arxiv` 为 `null` 的论文。
  新加的模型侧 `discipline` 字段只在**将来**抽取时生效，存量要靠重抽或专门 backfill。
- **词法检索的召回弱**：`query_warning` 只是把问题说出来，没有解决它。向量检索按要求已
  明确放弃，所以非拉丁语系 query 目前只能靠 `list_experience` 绕。
- **`utility` 字段仍未接入**：策略被采纳后的实际效果没有回写到置信度，"这条用过效果好"
  不会影响后续重排。
