# 论文经验抽取与利用

## 1. 背景与目标

论文阅读的结果不再只停留在当前对话中的摘要或笔记，而是被进一步沉淀为可检索、可复用、项目隔离的经验记忆（EvoMemory）。当前系统支持两条抽取路径：

| 路径 | 触发方式 | 用户感知 | 适用场景 |
| --- | --- | --- | --- |
| 主动抽取（Foreground） | 用户明确要求“从论文中提取/学习/保存经验”，由 `paper-experience` skill 触发 | 当前请求中立即完成并返回经验 | 用户指定论文，或围绕主题精选少量论文后学习 |
| 被动抽取（Background） | `paper-navigator` 完成检索并确定最终交付论文集后，调用 `enqueue_paper_experiences` | 不阻塞论文检索与回答，后台异步完成 | 日常检索过程中的经验自动积累 |

两条路径使用相同的全文下载、L1/L2 提示词、JSON 校验和项目经验存储，因此最终经验格式一致，可以统一检索和利用。

## 2. 总体流程

```text
论文 URL / ID / 主题
        │
        ├─ 主动：paper-experience
        │      └─ 解析/精选论文 → 下载全文 → L1、L2 并行抽取 → 校验归一化
        │                                      ↓
        │                              项目经验存储 + 立即返回
        │
        └─ 被动：paper-navigator
               └─ 搜索/筛选/排序 → 最终论文集 → 持久化队列 → 启动后台 worker
                                                        ↓
                                         领取任务 → 下载全文 → L1、L2 抽取
                                                        ↓
                                             校验归一化 → 存储 → 完成/失败

项目经验存储 → PAPER_EXPERIENCES.md（目录）
             → search_experience / list_experience（按学科内容检索与浏览）
             → read_memory（读单条完整记录）/ apply_experience（改绑到当前任务）
             → 后续 agent、skill 和对话复用
```

## 3. 主动抽取流程

1. **确定论文集合**：用户可以直接提供 URL、arXiv/DOI 等标识；也可以只给出主题，此时先用 `paper-navigator` 的规则检索并精选少量论文。默认精选 3 篇，显式指定时最多 5 篇，不会对全部搜索结果盲目抽取。
2. **调用 `extract_paper_experiences`**：工具在当前项目上下文中运行。对每篇论文，若项目中已有完整结果且未设置 `refresh=true`，直接复用缓存；否则下载全文并开始抽取。
3. **全文获取**：优先通过 Jina Reader 获取 Markdown/纯文本，失败时尝试直接文本响应；全文过短（少于 500 字符）会判定为失败，避免仅凭元数据或摘要生成经验。
4. **双层并行抽取**：同一篇论文同时执行 L1 实践经验和 L2 归纳经验提示词；多篇论文之间以并发上限 2 控制资源占用。
5. **严格校验与归一化**：要求模型只返回 JSON。运行时检查字段集合、数组结构、证据结构、L2 的 `claim_type` 等；随后注入稳定 ID、层级、来源 ID、初始置信度等运行时字段。
6. **持久化并返回**：L1/L2 JSON 和元数据原子写入当前项目；成功与失败按论文分别汇总返回，单篇失败不会吞掉其他论文的结果。

## 4. 被动抽取流程

`paper-navigator` 的搜索、筛选、阅读和回答流程保持不变。只有在 POINT、LIST 或 ITERATIVE 分支已经确定“最终要交付给用户的论文集”后，才调用一次 `enqueue_paper_experiences`，并传入每篇论文的可解析 URL、论文 ID、标题以及可获得的 arXiv 主分类。

### 4.1 入队与去重

- 队列按项目隔离，任务文件保存在 `paper_experience_queue/projects/<project_id>/` 下。
- 任务 ID 由项目 ID 与规范化论文标识稳定生成（`PX-...`），同一论文在 `pending`、`running` 或 `completed` 状态下再次入队都会被识别为已有任务。
- 已失败任务再次入队时会被恢复为 `pending`，清空旧错误并允许重试。
- 入队调用只负责持久化和尝试启动 worker，不等待抽取、不改变论文回答，也不把抽取状态混入用户的检索结果。

### 4.2 Worker 消费

后台 worker（LangGraph graph：`evomemory-paper-experience-worker`）按项目排他锁运行：

1. 启动时把上次中断遗留的 `running` 任务恢复为 `pending`；
2. 原子地把一个 `pending` 文件移动到 `running`，并递增 `attempts`；
3. 下载全文，加载 L1/L2 提示词，并并行调用抽取模型；
4. 抽取成功后写入经验存储，再将任务移动到 `completed`；
5. 任一步骤异常则记录错误信息并移动到 `failed`，继续处理队列中的其他任务。

这种设计使队列具备可恢复、可去重、可观察的生命周期，同时把耗时的网络和模型调用从论文检索主链路中解耦。

## 5. 抽取出的经验形式

每篇论文分别生成两个 JSON 文件：`l1.json` 和 `l2.json`。每个文件包含 `experiences` 数组；数组可以为空，表示论文没有足够证据支持该层经验。

### 5.1 L1：实践经验（Practical Experience）

L1 记录“在什么具体环境下做了什么，以及得到什么反馈”，强调可执行性和实验事实。每条记录的模型输出字段为：

| 字段 | 含义 |
| --- | --- |
| `domain` / `task` | 研究领域与具体任务 |
| `statement` | 自洽的实践经验陈述，包含问题、步骤、条件、结果和边界（提示词要求至少 350 字） |
| `applicable_when` / `not_applicable_when` | 适用前提与不适用边界 |
| `scope` | 模态、规模、模型/骨干和流水线阶段 |
| `action` / `effect` | 做法与观测到的效果，尽量保留指标和数字 |
| `practice_trace` | 3–6 个“行动 → 反馈”对，描述实践链路 |
| `evidence` | 一个或多个来源证据，包含章节和逐字引用；每条引用至少 150 字符 |

### 5.2 L2：归纳经验（Inductive Experience）

L2 把单篇论文中的结果提升为可迁移的作者支持的规律、比较判断或条件性结论，要求超出单个实验实例且去掉系统名称后仍然有用。

| 字段 | 含义 |
| --- | --- |
| `domain` / `task` | 研究领域与适用能力 |
| `statement` | 带条件、边界、证据模式和机制（若论文明确给出）的归纳陈述（提示词要求至少 350 字） |
| `claim_type` | `property`、`relation`、`trend` 或 `conditional` |
| `applicable_when` / `not_applicable_when` | 适用与排除条件 |
| `scope` | 模态、规模、测试模型和阶段边界 |
| `action` / `effect` | 可执行启示与观测/预期效果 |
| `rationale` / `rationale_depth` | 作者支持的因果解释及深度（`deep` / `shallow` / `null`） |
| `evidence` | 逐字来源证据；每条引用至少 150 字符 |

### 5.3 运行时补充字段

模型不输出的生命周期字段由运行时统一注入，避免模型伪造来源或 ID：

- `id`：稳定的 L1/L2 记录 ID；对外检索时表现为 `E-...`；
- `layer`：`L1` 或 `L2`；
- `paper_id`、`source_id`：论文及证据来源标识；
- `domain_arxiv`：可用时记录 arXiv 主分类；
- `confidence`：基于证据完整度、实践链长度或 rationale 的单篇初始置信度（上限 0.85）；
- `utility`：预留给后续使用反馈；初始为 `null`；
- 论文元数据：标题、URL、全文哈希、提示词哈希、提取时间、支持/反驳论文列表等。

## 6. 存储与项目隔离

每个项目拥有独立的经验空间，核心文件布局如下：

```text
/memories/
├── experiences/projects/<project_id>/<paper_storage_key>/
│   ├── metadata.json
│   ├── l1.json
│   └── l2.json
└── profile/projects/<project_id>/PAPER_EXPERIENCES.md
```

`l1.json`、`l2.json` 和 `metadata.json` 使用临时文件加原子替换写入；同一论文重新抽取会替换该论文的结果，而不会产生重复论文目录。`PAPER_EXPERIENCES.md` 是由 JSON 存储派生出的只读目录，便于 WebUI 浏览。

## 7. 经验如何被利用

经验存储与传统 observation 存储物理分离，检索入口也分离 —— 两个库回答的是不同的问题
（observation 记录本 agent 的工具和环境如何表现，experience 记录论文发现了什么），
共用一个入口会让 observation 那套词汇变成两者共同的词汇：

- `search_experience` 按**内容**检索论文经验：`topic` / `method` / `task` 三个主题面
  分别检索再用 RRF 融合，`discipline` / `domain` / `level` 是精确过滤。它不接受
  `memory_type` / `scope` —— 每条 `E-*` 都存为 semantic/project，传这两个参数只会
  静默清空结果集；
- `list_experience` 按结构浏览（discipline → domain → records，每层都分页并报总数）。
  词法检索的前提是调用方已经知道库里的说法，开放式问题往往没有唯一正确的问法，
  浏览绕开了措辞问题；
- `search_observations` 只检索 `O-*`，面向过程的问法（"该怎么做…"）属于这里；
- `read_memory` 通过稳定的 `E-...` ID 读取完整经验 JSON；
- `apply_experience` 在需要**做决策**而非补充上下文时使用：它把来源里写死的值改绑到
  当前任务上，而不是让调用方照抄；
- 后续 agent/skill 可以把经验作为上下文，用于方案设计、实验规划、参数选择、风险边界判断和论文阅读；
- 同一项目内共享经验，不同项目之间不会互相污染。

因此，系统形成“论文检索 → 经验抽取 → 项目记忆 → 检索复用”的闭环：主动路径保证用户明确要求时即时学习，被动路径则把日常检索转化为持续的知识积累。

## 8. 可靠性与边界

- **证据优先**：没有全文证据就不生成经验；解析失败、字段缺失或引用格式不合法会让该篇任务失败，而不是写入不完整记录。
- **幂等与缓存**：主动抽取默认复用已有结果；被动入队按稳定任务 ID 去重；显式 `refresh` 才会重新抽取。
- **故障隔离**：主动批次按论文返回成功/失败；后台 worker 对单任务失败记错后继续消费。
- **可恢复**：worker 中断后会回收 `running` 任务；项目级文件锁避免多个 worker 同时消费同一队列。
- **适用范围**：经验是基于论文作者报告和引用证据的可复用记录，不等同于对所有任务、模型或数据集都成立的普遍定律；`applicable_when`、`not_applicable_when` 与 `scope` 用于保留边界。

## 9. 汇报时可强调的价值

1. **从“读过”到“会用”**：论文信息被拆解为行动链和可迁移规律，而不是一次性摘要。
2. **在线体验与后台积累兼顾**：主动抽取即时反馈，被动抽取不阻塞检索主流程。
3. **结构化、可验证、可追溯**：L1/L2 schema 固定，保留章节级逐字证据和论文元数据。
4. **项目化记忆**：不同研究项目独立存储，可通过统一检索接口按需召回。
5. **面向持续进化**：`confidence`、`utility`、支持/反驳论文等字段为后续经验聚合、效果反馈和经验更新预留了接口。
