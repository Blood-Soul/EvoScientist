# 论文经验库系统 · 汇报材料

> 面向下午工作汇报。含系统概述、可现场演示的 Query、以及每个 Query 的预期看点。

---

## 一、一句话说清做了什么

把论文从「读完就忘」变成**可检索、可复用、可追溯的经验资产**，并打通了三个环节：

```
      论文 ──产──> 经验库(374条) <──用── 问答（带依据链）
                       │
                       └──验── 经验 vs 原文 对比实验
```

| 环节 | 技能 | 解决什么 |
|---|---|---|
| **产** | `paper-experience` | 论文 → 结构化 L1 实践经验 + L2 归纳经验，可沉淀入库 |
| **用** | `experience-answer` | 拿现成经验库回答问题，并给出依据链 |
| **验** | `solution-ab` | 同一问题，用「经验」和「原文」各出一份方案分列对比，检验经验库是否真有价值 |

## 二、经验库现状

| 指标 | 数值 |
|---|---|
| 经验总量 | **374 条** |
| 覆盖论文 | **51 篇** |
| 来源构成 | 离线库批量导入 336 · 在线抽取沉淀 24 · 会话蒸馏 14 |
| 类型分布 | L2 归纳经验（semantic）245 · L1 实践经验（procedural）129 |
| 知识图谱 | **95% 节点有边**，最大连通分量 338 节点（90%） |

### 两层经验的区别

| | L1 实践经验 | L2 归纳经验 |
|---|---|---|
| 回答 | 在某环境为某目标**做了什么、得到什么反馈** | 某情境下可提出**什么规律性断言** |
| 核心字段 | `practice_trace`（action→feedback 链）、实践环境、任务上下文 | `declaration`、`claim_type`、因果解释 `r`、置信度 `μ` |
| 粒度 | coarse / medium / fine 三级 | property / relation / trend / conditional 四类 |
| 存储类型 | `procedural` | `semantic` |

每条经验都带 **≥450 词自包含叙述** + **原文引用** + **5 套领域分类**，可溯源到具体论文章节。

## 三、现场演示 Query（按推荐顺序）

> 全部为**日常开发场景**，且已实测确认库中有真实经验支撑。
> 打开 http://localhost:4716，逐条发送。

### Query 1 · 评测方法选择（最推荐开场）

```
用经验库回答：评估代码生成模型时，用 BLEU 分数靠谱吗？该用什么指标？
```

**为什么用它开场**：库中有 **三条独立经验**（分数 74.4 / 61.0 / 56.5）从不同角度指向同一结论 —— 这种**多来源交叉印证**最能体现经验库的价值，而不是单篇论文的孤立观点。

**预期看点**：
- 明确回答 BLEU 不适合，并给出替代方案（测试用例通过率 / pass@k）
- 依据链引用多篇论文（含 APPS benchmark、Codex 相关研究）
- 会说明适用边界（哪些场景下 BLEU 仍有参考价值）

**开发相关性**：任何做代码相关模型/工具评测的团队都会踩这个坑。

---

### Query 2 · Prompt 工程实操

```
用经验库回答：few-shot prompt 里的示例该怎么挑？换示例对效果影响有多大？
```

**预期看点**：
- 命中一条 46.6 分的 `[property]` 类经验，明确指出**示例的选择对结果影响很大**（不是"稍有影响"）
- 会带出 DSPy 相关经验（把 prompt 编译当作优化问题而非手工调参）
- 依据链会区分「实验观测」与「作者归纳」

**开发相关性**：直接影响日常 prompt 调优的工作方式 —— 如果示例选择方差很大，手工试错就不可靠。

---

### Query 3 · 端侧部署优化

```
用经验库回答：把多模态模型部署到手机端，性能瓶颈在哪？有哪些优化手段？
```

**预期看点**：
- 命中一条 68.0 分的 `[conditional]` 经验，含一整套端侧优化组合（顺序内存加载、量化等）
- 另有一条明确指出**首要速度瓶颈在哪个环节**（`[property]` 类）
- 会给出具体数值和硬件条件

**开发相关性**：工程落地问题，有明确的取舍决策。

---

### Query 4 · Agent 失败恢复（已验证过的深度案例）

```
用经验库回答：如何让 coding agent 从执行失败中迭代改进？
```

**预期看点**（此 Query 已完整跑通，可作为保底演示）：
- 综合 4 条经验给出**闭环方案**：失败 → 归因 → 定向修复 → 再执行 → 沉淀失败模式
- 引用真实实验数据：Base 50% → Reflexion 60% → 固定 checklist 68% → 本地失败分类法 70%
- **边界部分尤其体现质量**：会主动说明 TextGrad 的 36% 来自 39 道确定性算法题、不能等比例迁移到开放式仓库修复；SWE-agent 的 70% 来自 Verified Mini，不同 harness 不可横比

---

### Query 5 · 诚实边界演示（**建议一定要演**）

```
用经验库回答：如何优化 CUDA kernel 的访存合并？
```

**这一条演的是「系统不会胡说」**。

库中完全没有 CUDA 相关经验。但因为检索是关键词匹配，**它不会返回零命中，而是返回高分噪音**：

| 查询 | 首条命中 | 分数 |
|---|---|---|
| `CUDA kernel memory coalescing` | 一条讲 Polyak-Łojasiewicz 不等式的经验 | **28.1** |

28.1 分与真实命中同一量级（对比 Query 1 首条为 74.4，Query 4 首条为 41.9）。**若只看分数不读内容，很容易编出一篇像样但完全错误的答案。**

**预期表现**：
- 明确回答「经验库未覆盖」
- 逐条列出召回到什么、为什么判为不相关（会指出是 `memory`/`optimization` 撞词）
- 列出缺口清单（warp 地址连续性、bank conflict、向量化访存…）
- 给出补库路径（抽取 CUDA 性能论文后沉淀）

**汇报价值**：可信度来自「知道自己不知道什么」。这一条比任何成功案例更能说明系统可用于生产。

### Query 6 · 方法论实验（时间充裕时演）

```
用 solution-ab，论文 2509.25370,2411.19547,2607.16387，问题是"如何让 agent 从执行失败中迭代改进"，分列对比。自己执行不要派 subagent。
```

**预期看点** —— 同一问题、同一骨架、只换上下文（经验 vs 原文），并排展示：

| | A 组（抽取经验） | B 组（论文原文） |
|---|---|---|
| 强项 | **抽象成可复用架构** —— 三篇合成「诊断→分类法→训练」闭环，原文中无任何一篇提出过 | **保住可复现配置** —— `κ≥0.75`、最多 3 次修复、`5e-5→5e-6` 余弦退火 |
| 关键数值出现次数 | 19 次（反复带在多个自包含叙述中） | 1 次（只在原始表格） |

**结论**：**做架构决策用经验，要复现实验用原文** —— 两者不是替代关系。

耗时约 5–8 分钟（两次长上下文生成），时间紧可跳过，用本文表格直接讲。

## 六、技术要点（被问到时用）

### 抽取质量保证

- 每条经验含 **≥450 词自包含叙述**，读者无需查原论文即可应用
- **≥150 字符原文引用** + 章节标记，可溯源
- L2 的因果解释 `r` 必须能追到论文原句，**不允许模型自行推理**

### 检索机制与已知限制

- 原生 TF-IDF 关键词检索（id×5 / summary×3 / body×1 权重）
- **无语义兜底** —— 同义改写可能漏召，因此查询词拆解是效果关键
- 库外主题返回高分噪音而非零命中（见 Query 5），因此判相关性**必须读语义、不能靠分数阈值**

### 两阶段召回（控制成本）

单条经验约 9,600 字符。因此：先 `search_observations` 拿摘要粗筛（每条 1 行），再对真正相关的 3–5 条读全文。避免 4–8 万字符的无关正文淹没答案。

### 沉淀与幂等

- 在线抽取的经验可一键沉淀入库，内容 hash 去重，**重复运行安全**
- L1 → `procedural`，L2 → `semantic`，与离线库映射一致，混合检索无语义冲突

## 八、开发过程中修掉的坑（体现工程量，被问到时用）

打通链路过程中定位并修复了 **9 个问题**，其中 6 个是原有缺陷。三个最有代表性的：

### 1. 模型名前缀导致全链路 503

WebUI 发任何消息都报 `503 Pricing configuration is temporarily unavailable`，但 curl 直测端点 200。抓包对比才发现请求体差异：

```
EvoScientist 发:  "model": "openai/gpt-5.6-terra"   → 503
curl 发:          "model": "gpt-5.6-terra"          → 200
```

模型注册表缺 `custom-openai` 条目，查找时 fallback 用了 openrouter 那条带前缀的 id，代理端定价表查不到即报 503。**503 的真实含义是"模型名不认识"。**

### 2. Agent 说"没有 execute 工具"是事实，不是幻觉

`tool_selector` 中间件每轮用 LLM 挑选暴露给 agent 的工具，其"永不过滤"白名单原本只有 5 项，**`execute` 和抽取工具都不在内**。而 `task` 恰在白名单中 —— 所以工具被滤掉时 agent 手上只剩 `task`，就反复去派 subagent，看起来像"不听指令"，实际是没别的可用。

### 3. 补丁手测通过、agent 跑无效 —— 静默降级

agent 的 `execute` 跑裸 `python3`，项目依赖只在 venv 里。给抓取脚本打的直连补丁在 `uv run` 下测试通过，但 agent 跑时 `import pymupdf` 抛 `ImportError` → 被 `except` 捕获 → **静默回退到不通的 Jina** → 卡到超时。表现像"补丁没生效"，实为悄然降级。

解法是脚本自动 re-exec 进 venv。一个细节：探测目标必须是**真正需要的深层第三方依赖**，探顶层包会导入成功、跳过 re-exec，然后炸在更深处。

> 完整 9 个问题的现象/根因/修复见 `docs/report/milestone-paper-experience.md`。
