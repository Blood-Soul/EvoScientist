# experience-answer 验证报告：查经验库答题与诚实边界

## 一句话总结

新增 `experience-answer` 技能补上经验库的消费端；命中与未命中两个场景均通过验证，其中「未命中时诚实报告」的表现比命中更有说服力 —— 它拒绝了一条 28.1 分的高分噪音，而非据此编造答案。

---

## 一、补上的缺口

经验库此前只有生产端没有消费端：

| 技能 | 职责 | 状态 |
|---|---|---|
| `paper-experience` | **产** —— 论文 → L1/L2 经验，可沉淀入库 | 已有 |
| `solution-ab` | **验** —— 经验 vs 原文对比，检验经验库价值 | 已有 |
| `experience-answer` | **用** —— 查库答题 + 依据链 | **本次新增** |

在此之前，「拿现成经验库回答我的问题」只能靠 agent 每轮 preflight 被动检索，命中什么算什么，没有为答题优化的流程。

### 交付物

```
skills/experience-answer/
└── SKILL.md          # 纯编排，零脚本
```

不需要 Python 脚本 —— `search_observations` / `read_memory` 都是 agent 常驻工具（已在 tool_selector 白名单中）。

## 二、设计：两阶段召回

### 核心约束：单条 observation 约 9,600 字符

召回 5–8 条全文读 = 4–8 万字符，答案会被埋在大量无关正文里。因此分两阶段：

| 阶段 | 动作 | 读什么 |
|---|---|---|
| **粗筛** | `search_observations(limit=8)`，多查询去重 | 仅 `summary`（1 行）+ 分数 + `memory_type` |
| **精读** | 对存活的 **3–5 条** `read_memory` | 按需读小节，非通读全文 |

SKILL.md 明确了各小节用途，避免 agent 通读 9,600 字符：

| 小节 | 用途 |
|---|---|
| `Narrative` | 主体，答案主要来源 |
| `Practice trace` | L1 的 action→feedback，要具体步骤时看 |
| `Causal explanation (r)` | L2 的因果机制，回答「为什么」时看 |
| `Applicability context` / `Task context` | 边界条件，判断是否适用于用户场景 |
| `Source` / `Verbatim quote` | 溯源，写依据链用 |

### 输出结构：答案在前，依据链在后

```
## 回答          ← 综合多条，不逐条罗列
## 依据链
   用到的经验     ← 表格：经验 / 类型 / arXiv 出处 / 贡献了什么
   推理过程       ← 检索 → 筛选 → 综合 → 边界
   覆盖缺口       ← 库里没覆盖的，明说
```

## 三、关键发现：库外主题返回高分噪音，不是零命中

这是写 SKILL.md 之前实测得到的，直接决定了「如何判相关性」的规则。

### 实测数据

| 查询 | 首条命中 | 分数 |
|---|---|---|
| `CUDA kernel memory coalescing optimization` | 一条讲 **Polyak-Łojasiewicz 不等式**的经验 | **28.1** |
| `sourdough bread fermentation temperature` | 一条讲 **program synthesis 采样温度**的经验 | **14.6** |

两条都靠 `memory` / `optimization` / `temperature` 撞词命中，主题完全无关。

### 为什么这很危险

28.1 分不算低 —— 对比命中场景的首条是 41.9 分，同一量级。**如果只看分数不读内容，agent 会把它当成命中，然后编出一个像样但完全错误的答案。**

更麻烦的是这种错误难以察觉：答案结构完整、有出处标注，只是出处与内容毫无关系。

### 补充背景

库中还有物理学论文（πΣ 不变质量分布、手征扰动理论）、优化理论等 agent 研究之外的内容，覆盖面比预想的杂 —— 这正是纯关键词召回会误导的根源。

### 写进 SKILL.md 的规则

把上述两个真实案例连同分数一起写入正文，并规定：

> **判相关性靠读 summary 语义，不靠分数。** 分数断崖（40 → 12）是有用的提示，但绝不能替代阅读。跑题的条目不管分数多高都要丢。

## 四、验证结果

### 场景一：命中（库中有 3 篇相关论文的 24 条经验）

问题：如何让 coding agent 从执行失败中迭代改进？

| 检查项 | 结果 |
|---|---|
| 引用真实性 | ✅ 四条经验，三条来自本项目抽取的论文（2607.16387 / 2509.25370） |
| 数值可溯源 | ✅ Base 50% → Reflexion 60% → 固定 checklist 68% → 本地 taxonomy 70%，该串数字确实存在于 `Practice trace` |
| 综合而非罗列 | ✅ 五个维度整合成一个闭环（反馈 → 归因 → 检查点 → 分类法 → 记忆压缩） |
| 依据链完整 | ✅ 每条标注类型、arXiv 出处、对回答的贡献 |
| 边界诚实 | ✅ 见下 |

**边界一节的质量值得单独说明**。它主动指出：

- TextGrad 的 36% 来自 39 道确定性算法题，**未证明可等比例迁移到开放式仓库修复**
- SWE-agent 的 70% 来自 SWE-bench Verified Mini，**不同 harness 不应直接横比**
- 根因 taxonomy 依赖足够详细的轨迹与中间状态，**原研究人工标注一致性仅为中等**

这些限定条件是从经验的 `Applicability context` 字段读出来的实际内容，不是套话 —— 也印证了字段补全那次重导的价值（旧版导入器会丢掉这些字段）。

### 场景二：未命中（这是更重要的考验）

问题：如何优化 CUDA kernel 的访存合并？

它**没有掉进 28.1 分的陷阱**：

| 行为 | 表现 |
|---|---|
| 逐条列出召回结果并说明为何不相关 | ✅ 四条全部列出并给出判定理由 |
| 识别出撞词命中 | ✅ 准确指出 `O-63966232be64a946`（PL 不等式）是匹配到泛化词 "memory/optimization" |
| 拒绝外推 | ✅ 明确「不能作为 CUDA 访存合并建议的证据」 |
| 列出缺口清单 | ✅ warp 地址连续性、bank conflict、`float4` 向量化、Nsight Compute 指标、架构差异等 |
| 给出补库路径 | ✅ 提示抽取 CUDA 性能论文后经 `paper-experience` 沉淀 |

值得注意：它识别出的 `O-63966232be64a946` **正是我实测时撞见的同一条**记录。SKILL.md 里那条约束直接命中了这个场景。
