# solution-ab 验证报告：经验 vs 原文的方案对比

## 一句话总结

新增 `solution-ab` 技能，用同一问题、同一骨架、只换上下文的方式生成两份方案并分列对比；经文件层核验确认 agent 真实调用了技能而非自行编造；同时打通了在线抽取经验沉淀进 EvoMemory 的最后一环。

---

## 一、新增技能：solution-ab

### 目的

`paper-experience` 能把论文抽成 L1/L2 结构化经验，但抽完即止 —— 无法回答「这些经验相比直接读原文，到底强在哪、弱在哪」。`solution-ab` 补上这个下游消费环节。

### 交付物

```
skills/solution-ab/
├── SKILL.md                       # 编排 + 分列输出规范
├── scripts/build_contexts.py      # 去噪 + 多篇合并
└── references/solution-template.md # A/B 共用 6 节骨架
```

### 设计核心：控制变量

同一问题、同一骨架、同一生成要求，**唯一变量是上下文**：

- **A 组** = 抽取的 L1/L2 经验（`rendered.md`）
- **B 组** = 论文正文（已剔除 References/附录）

为使差异真正归因于上下文，SKILL.md 立了四条硬规则：

| 规则 | 理由 |
|---|---|
| **隔离生成** | 写 A 时当 B 不存在，禁止「相比另一方案…」 |
| **只用给定上下文** | 掺入模型自身先验会让差异不再归因于上下文 |
| **缺失即信号** | 覆盖不到就写「上下文未覆盖」；编造填补会掩盖最有价值的信号 |
| **数值可溯源** | A 引经验条目 id，B 引论文章节/表格 |

### 不做裁判

明确禁止打分、排名、宣布优劣或推荐用哪种上下文。只陈述各自内容与分歧点，评判权归用户。区分了两件事：

- ✅ 允许：陈述可核查事实 —— 「A 未提及 ablation 数据，B 引用了 Table 3 的 9.8 个百分点」
- ❌ 禁止：将其转为判断 —— 「B 更全面」

## 二、关键发现：去噪是公平对比的前提

### References/附录占论文 15–46%

这部分对方案设计毫无价值，却会严重扭曲规模对比：

| 论文 | 全文 | 正文 | 尾部占比 |
|---|---|---|---|
| 2410.01242 | 43,882 | 32,749 | 25% |
| 2303.11366 | 73,649 | 43,833 | 41% |
| 2502.13172 | 98,796 | 54,015 | 46% |
| 2210.03629 | 50,242 | 42,819 | 15% |

### 去噪对差异的影响

以最终实验的三篇为例：

| | 去噪前 | 去噪后 |
|---|---|---|
| A/B 规模差异 | 54% | **13.6%** |
| 删除量 | — | 104,493 字符 |

**不去噪的话，B 组「更长」里有相当比例是参考文献**，对比就失真了 —— 差异会被误读为格式特性，实际只是噪音体积。

### 反直觉的结果

去噪后**反而 A 组（经验）更长**。原因是每条经验含 ≥450 词 narrative，而论文正文相对紧凑。这否定了「经验必然更省 token」的朴素预期，也说明真正要检验的不是压缩率，而是**单位 token 的信息效用**。

### 容差策略

`build_contexts.py` 在差异超过 35% 时发出警告，要求在输出中如实标注「对比非等长」。不做复杂采样 —— 实测多篇合并时差异天然收敛（三篇为 13.6%），单篇才可能超标（RGD 为 55%，因其原文本身偏短）。

## 三、多篇合并设计

支持 1–3 篇，合并成两个大上下文，**跨论文综合出一份方案**（非逐篇作答）。

- 两组必须覆盖同一论文集，否则差异反映的是「各自看了哪些论文」
- 引用带论文 id：`2509.25370 L2-002` / `2410.01242 §III-B`
- 上下文以 `# === Paper <id> · … ===` 分隔

## 四、触发方式：两种并存

| 方式 | 说明 |
|---|---|
| **链式** | `paper-experience` 抽完后，**仅在用户显式要求对比时**转交 `solution-ab` |
| **独立** | 直接调用 `solution-ab`，传入 problem + paper ids |

裸的「抽取经验」请求不触发对比 —— 避免每次抽取都额外烧 5–8 分钟。

## 五、论文选取：相关性优先于可用性

### 一次自我纠正

初次试跑时我用了「刚好抽好的四篇」，其中包含 *Unveiling Privacy Risks in LLM Agent Memory*（`agent_safety`）—— 它与「从执行失败中迭代改进」毫无关系，纯属凑数。用户直接指出「是不是只为了堆料」。

这个问题是实质性的：**无关论文会让两组上下文各含约 1/3 噪音，差异更难归因**。

### 改为让 agent 按主题检索

主题 `LLM agent self-improvement from execution feedback and failure`，取前 3 篇：

| 论文 | 切入角度 | domain | L1/L2 |
|---|---|---|---|
| **2509.25370** *Where LLM Agents Fail and How They can Learn From Failures* | 诊断 | `agent_learning` | 5/3 |
| **2411.19547** *Training Agents with Weakly Supervised Feedback from LLMs* | 训练信号 | `agent_learning` | 5/2 |
| **2607.16387** *Fantastic Adaptive Taxonomies and How to Use Them* | 改进机制 | `agent_learning` / `agent_software_eng` / `agent_memory` | 5/4 |

诊断 → 信号 → 机制，三层互补不重复。

**一处误判记录**：我曾怀疑第三篇跑题（标题是 Harry Potter 梗），查其 Related Work 小节（*Failure taxonomies for agent systems* / *Improving agents from execution traces*）与抽出的 declaration 后确认高度对题。**不能凭标题判断相关性。**

## 六、文件层核验：确认真实调用技能

用户质疑「是用到 skill 了还是自己编的」。不看 agent 转述，直接查磁盘。

| 核验项 | 方法 | 结果 |
|---|---|---|
| 脚本真执行 | 先清空 `artifacts/ab/`，检查是否重新生成 | ✅ 22:50 重新生成，三篇各出现 1 次 |
| 真读了上下文 | 报告字符数 vs 实际文件大小 | ✅ A 161,740/162,060、B 142,318/144,105（0.2–1.3% 口径差） |
| **引用 id 真实** | 所引 `L1-003/004/005`、`L2-001/002/003` 是否存在于上下文 | ✅ 全部命中，**无虚构 id** |
| 数值可溯源 | 抽查 7 个关键数字 | ✅ `97.2` `70.0` `45.0` `24.3` `0.75` `0.70` `0.14` 全部命中 |
| 跨论文综合 | 是否合成一份方案 | ✅ 三篇合成为「诊断→taxonomy→训练」闭环 |
| 守住不判胜负 | 差异观察中是否出现优劣判断 | ✅ 全为描述性，无「A 更好」类表述 |

**引用 id 核验是最强证据** —— 若为编造，极易引到不存在的 `L1-006` 或漏引。实际引用分布与各篇真实条目数完全吻合（2411.19547 仅有 L2-001/002，其引用即止于此）。

## 七、实验发现

这次对比产出了有实际价值的差异：

### A 组（经验）擅长抽象成可复用架构

它把三篇压成「即时恢复 / 跨轨迹诊断 / 离线参数更新」三层闭环 —— **这个框架三篇论文中没有任何一篇明确提出**，是跨论文综合的产物。

### B 组（原文）保住可复现的配置细节

`κ≥0.75`、`coverage≥0.70`、最多 3 次检查点修复、`5e-5→5e-6` 余弦退火 —— 这些参数在经验的 narrative 叙述中被稀释了。

### 一个量化观察

关键数值在两组的分布差异明显，例如 critic precision `70.0`：

| | A 组 | B 组 |
|---|---|---|
| `70.0` 出现次数 | 19 | 1 |
| `97.2` 出现次数 | 9 | 1 |

经验会把同一关键数值反复带在多个条目里（因每条 narrative 自包含），原文只在原始表格出现一次。这解释了为何 A 组在 13.6% 更长的情况下**细节反而更少** —— token 花在了叙述性解释与重复上，而非参数覆盖面。

### 对经验库定位的输入

**做架构决策用经验，要复现实验用原文。** 两者不是替代关系。

## 八、打通最后一环：在线经验沉淀

`promote_to_memory.py` 此前只验证过 import 与路径定位，**真实写入一直未验证**。本次补齐。

### 修复：第三次遇到同一类坑

脚本装到全局后报 `ModuleNotFoundError: No module named 'EvoScientist'`，随后又报 `No module named 'langchain'`。

根因与此前的 fetcher、`scholar_search.py` 完全一致：**agent 的 `execute` 跑裸 `/usr/bin/python3`，项目依赖只装在 venv 里**。

一个值得记录的细节：初版 re-exec 探测的是顶层包 `EvoScientist` —— 它在加了 `REPO_CANDIDATES` 后能导入成功，于是**跳过了 re-exec**，然后在更深处炸在 langchain 上。**探测目标必须是真正需要的第三方深层依赖**，而非顶层包。

### 验证结果

| 检查项 | 结果 |
|---|---|
| dry-run 定位 | ✅ 三篇分别 queued 8 / 7 / 9 条，与抽取结果吻合 |
| 真实写入 | ✅ observation 总数 **349 → 373**，正好 +24 |
| 幂等性 | ✅ 重跑 `Created: 0 / Duplicate: 8`，总数不变 |
| 来源统计 | ✅ 336 `experience-bank`（离线）+ 24 `paper-experience`（在线） |

### 召回验证

| 查询 | 首位命中得分 |
|---|---|
| `agent failure taxonomy execution trace` | **66.2** |
| `critic precision weakly supervised feedback` | **55.3** |
| `critical error replay recovery` | **25.0** |

三条查询全部命中刚沉淀的经验。

### 沉淀触发：两种方式

| 方式 | 示例 |
|---|---|
| **一段式** | 「抽取这篇论文的经验并沉淀到记忆」 |
| **追加式** | 「把刚才抽的经验存进记忆」 |

追加式不重新抽取 —— 缓存仍在磁盘，直接沉淀该轮的 paper ids。未经要求不主动沉淀。

## 十、待办

1. **`solution-ab` 接入大经验库** —— 当前只对比「单篇/多篇的经验 vs 原文」。可加「C 组：336 条 observation 检索」，检验跨论文经验库相比单篇经验的增益。Step 2 的上下文构建设计已预留扩展空间。
